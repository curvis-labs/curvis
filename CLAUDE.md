# Curvis — instructions for Claude Code

Curvis is an open-source desktop app for scientific data analysis and plotting (comparable to GraphPad Prism).
Priorities, in order: **correct statistics**, **an easy UI**, **fast processing**.

- Product spec: `docs/SPEC.md` — the source of truth for features. Do not add features that are not in it.
- Build plan: `docs/PHASES.md` — phases, steps and acceptance criteria. Work on one step at a time.
- If the spec is ambiguous or a step conflicts with these rules, stop and ask. Do not guess.

## Stack

| Concern | Use |
| --- | --- |
| Language / env | Python 3.12, managed with `uv` |
| UI | PySide6 (Qt 6). Qt model/view for tables |
| Data | NumPy arrays per column; Polars for import and bulk operations; Apache Arrow (pyarrow) on disk |
| Excel import | `fastexcel` (.xlsx), `xlrd` (.xls) |
| Statistics | SciPy, statsmodels, scikit-posthocs (Dunn) |
| Curve fitting | lmfit |
| Survival | lifelines |
| Live plots | pyqtgraph |
| Export plots | Matplotlib (PNG, SVG, PDF) |
| Formula parser | Lark (no `eval`, no `exec`, ever) |
| Tests | pytest, pytest-qt, hypothesis, pytest-benchmark |
| Lint / types | ruff (lint + format), mypy (strict on `core`, `formula`, `analysis`, `io`) |
| Packaging | PyInstaller |

Do not add a dependency that is not in this table without asking first.

## Commands

```bash
uv sync                          # install
uv run curvis                    # start the app
uv run pytest                    # all tests
uv run pytest tests/validation   # statistics vs. R reference results
uv run pytest tests/bench --benchmark-only
uv run ruff check . && uv run ruff format --check . && uv run mypy src
Rscript validation/r/generate_all.R   # regenerate reference fixtures (needs R)
```

Run lint, types and the relevant tests before saying a step is done.

## Layout

```
src/curvis/
  core/        document model, commands + undo stack, change log, dependency graph
  data/        columns, roles, groups, tables
  formula/     grammar, parser, compiler to NumPy, constants
  analysis/    base classes + registry; compare/, fit/, survival/
  compute/     job scheduler, thread + process workers
  charts/      chart spec; render_qt/ (pyqtgraph), render_mpl/ (Matplotlib)
  io/          .cvp project format, CSV/Excel import, Prism import
  ui/          main window, launcher, table view, dialogs, results panel
  settings/    app settings and global constants
tests/
  unit/ ui/ validation/ bench/
  validation/fixtures/   JSON reference results generated by R (committed)
validation/r/            R scripts that generate the fixtures
docs/                    SPEC.md, PHASES.md
```

## Architecture rules (do not break these)

1. **The UI never computes.** Widgets read from the document model and send commands. Any calculation that can exceed ~5 ms goes through `compute.scheduler`.
2. **The document is plain data.** Tables, calculated columns, analyses and graphs are serializable definitions (dataclasses). Analyses store their *inputs and parameters*, not just outputs. Graphs store a chart spec, not pixels.
3. **Every mutation is a Command** with `do()` and `undo()`, pushed on the per-document undo stack (max 50 steps). Every executed command is also appended to the document's change log (timestamp, command type, summary). Never mutate the model outside a command.
4. **Dependency graph.** Calculated columns, analyses and graphs declare what they read. After a change, mark only downstream nodes stale and recompute them in dependency order.
5. **Scheduler.** Debounce edits (~150 ms); a newer job for the same node cancels the older one. Small jobs run on a thread; heavy jobs (many fits, big imports, export) run in a process pool with arrays in shared memory.
6. **One chart spec, two renderers.** pyqtgraph draws on screen, Matplotlib exports. Both read the same spec. The Format dialog edits only the spec.
7. **Project files (`.cvp`)** are a zip: `project.json` (definitions, constants, settings, `schema_version`, change log) + one Arrow file per table. Save to a temp file, then rename. Bump `schema_version` and add a migration for every format change.
8. **Formulas are parsed, never evaluated as Python.**
9. **Lazy imports** for statsmodels, lifelines, Matplotlib and lmfit, so start-up stays under 1.5 s.

## Statistics: validation rules (most important section)

- Every analysis has reference results in `tests/validation/fixtures/`, generated by R scripts in `validation/r/` using established packages (`stats`, `emmeans`, `multcomp`, `PMCMRplus` or `dunn.test`, `drc`, `minpack.lm`, `survival`).
- **Write the R script and fixtures before the Python implementation.** Show the R script to the user for review before implementing.
- **Never edit a fixture or loosen a tolerance to make a test pass.** If Python and R disagree, find out why and report it. A documented, intentional difference needs the user's approval.
- Tolerances: test statistics and p-values 1e-8 relative; fitted parameters 1e-6; confidence intervals 1e-4. The only exceptions are those listed, with a reason and the user's approval, in `tests/validation/TOLERANCES.md` (e.g. Dunnett p-values, which both SciPy and R compute by numerical integration).
- Nonlinear fits must also pass the NIST StRD nonlinear regression datasets that apply.
- Each analysis needs edge-case fixtures: n = 2, ties, missing values, unbalanced groups, constant data, and a fit that cannot converge.
- Results must report method names exactly (e.g. "Dunnett's multiple comparisons test") and the p-value thresholds used for stars: * < 0.05, ** < 0.01, *** < 0.001.

## Performance targets (enforced by `tests/bench`)

| Operation | Target |
| --- | --- |
| Cold start to launcher | < 1.5 s |
| Open a 10 MB project | < 1 s |
| Import 100,000-row CSV | < 1 s |
| Scroll a 1,000,000-cell table | 60 fps |
| Recalculate a formula column, 100,000 rows | < 50 ms |
| t-test or one-way ANOVA, 10,000 points | < 20 ms |
| 4PL fit, 12 points × 20 series | < 200 ms |
| Graph redraw after a data edit | < 50 ms |
| Export a 300 dpi PDF/PNG | < 1 s |

A change that makes a benchmark more than 15% slower is a failure.

## UI conventions

- Sensible defaults: every dialog works with one click on OK for the common case. Advanced options go in a collapsed section.
- Results show a one-line plain-language reading next to the numbers, and warnings when assumptions look violated.
- Every action is reachable by keyboard; add it to the command palette (Ctrl+K).
- Light and dark themes: use palette roles, never hard-coded colors.
- User-facing text: short, plain English, sentence case.

## Working style

- One step from `docs/PHASES.md` per session. Start in plan mode, show the plan, then implement.
- Small commits with clear messages; one branch per step.
- Write tests alongside code. UI code gets pytest-qt tests for its main paths.
- At the end of a step, report: what was built, test and benchmark results, anything skipped, and open questions.
- Do not mark a step done if any test, lint or type check fails.
